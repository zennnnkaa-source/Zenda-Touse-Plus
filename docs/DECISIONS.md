## New Phase 1 decisions

### D-015 — Separate Lab module and target module — LOCKED for this phase

`lab` is the privileged bootstrap/probe client. `input-target` is a separate application package that logs real events delivered to it. This separation means a test can observe whether input crosses the app boundary rather than logging from the same caller that issued it.

### D-016 — No fake PASS state — LOCKED

A status can say `Binder connected`, `Permission granted`, `Pairing succeeded`, `ADB shell probe returned`, or `Tap command completed`; none of these text statuses is equivalent to verified input delivery. Only the observed target event log, with device and OS recorded, may be entered as a delivered-input result.

### D-017 — Explicit Gradle distribution in CI — PROVISIONAL

The authoring environment lacks an intact Gradle wrapper and Android SDK. Do not invent or ship a placeholder wrapper JAR. CI installs Gradle 9.6.0 and the declared Android SDK packages directly. Revisit after CI is green; then decide whether to add a verified wrapper generated by Gradle.

### D-018 — ADB only bootstraps the shared helper — LOCKED for Phase 1

The Lab wrapper permits only exact `id`, exact `pm path dev.zenda.inputbridge.lab`, and a strict generated `app_process` bootstrap command for the expected helper class, numeric high port and random session token. It does not expose a command text box or general shell terminal. Shizuku and direct ADB both use the same `LocalHelperServer` and `InputProbeCommandExecutor`; post-bootstrap `UID`, bounded `TAP x y` / `SWIPE x1 y1 x2 y2 durationMs`, and `STOP` requests use a short-lived authenticated loopback socket, not an ongoing ADB input pipe. Tests must use the dedicated test app or another explicitly authorized target.

### D-019 — Protect ADB identity bytes at rest — PROVISIONAL

The POC encrypts serialized private-key bytes using AES-GCM and an Android Keystore AES key. No production-security claim is made until the code compiles, persistence is tested across restart/key loss, dependencies are audited, and a specialist review is complete.

### D-020 — Phase 1 exit gate — LOCKED

Do not start Phase 2 until (a) CI build/tests are recorded, (b) at least one of the two activation paths has been exercised on a physical Android 11+ device, and (c) a real event is observed in the separate test target. If no path succeeds, report the technical blocker and keep Phase 1 open.


### D-015 In-place AndroidX UI foundation — LOCKED
Use the existing root project and existing `:lab` + `:input-target` modules. Add an AndroidX Navigation Compose app shell and reusable Material 3 theme inside `:lab`; do not create a separate Phase 2 repository/project. The test target remains a distinct application because it must independently record delivered events.

### D-016 Local preferences and probe history — LOCKED
Use DataStore for the non-sensitive dark/light theme preference. Use Room for bounded probe history with only fixed provider/action/outcome values and timestamps. Never persist pairing codes, ADB key material, arbitrary command output, or raw user-entered host/port data. Retain only the newest 100 history rows.

### D-017 Phase gate honesty — LOCKED
In-place Phase 2 foundation work may proceed at the user's explicit request, but Phase 1 remains **OPEN / NOT PASSED** until CI and a real physical-device input-to-target result meet the existing exit criteria. A release signing failure does not count as an input feasibility result.


### D-021 — In-place Phase 2 foundation — LOCKED
Continue in the existing Phase 1 repository and modules. Phase 2 is a repository milestone, not a separate project or new root. CI must pass on the exact current source revision before Phase 2 is marked PASS.

### D-022 — Destination-driven tab selection — LOCKED
The selected navigation item is derived from the current Navigation Compose destination route (exact route equality). Top-level tabs pop to the root and do not restore saved tab stacks in this small five-tab shell, avoiding an indicator that lags the visible destination. A focused unit test guards the route policy.

### D-023 — Guided Direct activation — PROVISIONAL
The default Direct flow opens the public Developer options Settings action, posts an ongoing waiting notification only when notification permission allows it, and uses `NsdManager` to discover current ADB pairing and connection endpoints. The user manually supplies only the six-digit temporary code in the normal path. After pairing, the flow auto-attempts connection, shell identity check, and the existing helper bootstrap. Manual host/port recovery stays available. This flow is experimental until tested on supported physical devices; it must never mark input delivery verified merely because pairing or shell identity succeeded.
